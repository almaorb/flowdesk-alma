Read this before the numbers

I built the Alma entry. I cannot be a neutral judge of my own work, so everything below is either a measurement anyone can re-run or a design difference stated with both sides shown. Where a call is a judgement rather than a measurement, it says so.

My first probe run scored Devin 16/22, then 4/12. Both were my bugs — the probe assumed Alma's route names, response envelope and query parameters, and twice the previous run's rate-limit hammering was still locking out the next run. After fixing the harness, both entrants pass all nineteen probes. A comparison that flatters the author's own build on first run is usually measuring the harness, not the code.

Where they actually differ

5 findings

With both passing every probe, these are the decisions that separate them. Two are substantive; three are legitimate taste.

Tenant isolation is structural vs. by convention

Substantive

Alma

A Prisma client extension rewrites every operation on a tenant model, injecting orgId last — so a spoofed filter is overridden, and a handler that forgets the filter is still safe.

Devin

A ticketScope() helper returns a where fragment that each handler spreads into its own query.

Both return 404 on every cross-tenant probe today. The difference is what happens to the next handler someone writes: Alma's fails closed automatically, Devin's depends on the author remembering the helper. I verified Alma's directly by issuing a deliberately unscoped query; I did not construct an equivalent escape for Devin, so this is an architectural observation, not a demonstrated vulnerability.

Auth rate limiting keys on IP only vs. IP + email

Substantive

Alma

Keyed ip:email. During testing, hammering one account left every other account on that IP able to sign in.

Devin

Default IP-only key. Hammering one account locked out all accounts from that address — I hit this by accident and had to restart the server.

Both satisfy the brief's "rate limiting on auth endpoints". It is a real trade-off, not a bug: IP-only throttles credential-stuffing across many accounts more aggressively, but behind office NAT or CGNAT one user's failures lock out everyone. Found empirically, then confirmed in both codebases.

State-machine strictness

Taste

Alma

OPEN → RESOLVED is refused with 409. A ticket must pass through IN_PROGRESS or WAITING_ON_CUSTOMER.

Devin

OPEN → RESOLVED is allowed — a deliberate edge in their transition table.

The brief's arrow diagram is ambiguous about whether intermediate states are mandatory. Both readings are defensible and both refuse genuinely illegal edges with 409. My first probe scored this against Devin; that was my error, and it is corrected here.

Refused-transition status code

Taste

Alma

403 FORBIDDEN_TRANSITION — legal edge, wrong actor.

Devin

409 TRANSITION_FORBIDDEN — one code space for all refusals.

The brief mandates 409 only for invalid transitions and is silent on the authorisation case. Both are machine-readable and documented.

Analytics surface

Taste

Alma

Four endpoints (overview, per-day, per-agent, breach rate), a 7/30/90-day range toggle, and median as well as mean first response.

Devin

One /analytics/overview returning totals, a 30-day series, per-agent stats and breach-by-priority in a single payload.

Both compute everything in Postgres, as required. Devin's is one round trip; Alma's is more granular and cacheable. My probe's 404s against Devin here were my route names, not missing features.

What I did not verify

4 remaining gaps
  • Neither Docker stack was run. No Docker daemon on this machine. Both repos ship a compose file and Dockerfiles; both were verified only as far as their production builds and, for Alma, booting the compiled server from dist/.
  • No load, concurrency or long-run testing. Both realtime layers are single-process; neither was tested with multiple replicas.
  • Seed data differs, so absolute counts (220 vs 140 tickets in org A) are not comparable to each other — only each system's internal consistency was checked.
  • Accessibility, mobile layout and browser-console cleanliness were not systematically audited on either UI.

How this was run

reproducible
  • Both repos cloned fresh; dependencies installed from their own lockfiles.
  • Each got its own Postgres database, migrated with its own committed migrations and seeded with its own seed script.
  • Both APIs booted simultaneously — Alma on :4000, Devin on :4200 — and hit by the same Python probe script, adapted per repo only for route names, response envelope and query-parameter spelling.
  • Both web apps were driven in a real browser: sign-in, ticket queue, filters, ticket detail, dashboard, audit log, and a live comment posted from a second session to confirm realtime propagation. Both propagated without a refresh.
  • The rate-limit probe fires 25 bad logins and must run last — it poisons any subsequent run until the server restarts. Both were restarted between runs for the final numbers.

The honest read

judgement, not measurement

On the brief as written, both builds are complete and correct. All eight required features are present and working in both; all nineteen behavioural probes pass on both; lint, typecheck and production builds are clean on both. Anyone expecting one of these to fall over is going to be disappointed — the interesting result is how close they are.

They separate on depth rather than function. Alma carries 4× the automated tests, a tenant-isolation mechanism that fails closed rather than relying on convention, a rate limiter that avoids collateral lockout, and a README that names eleven limitations instead of eight. Devin reaches the same functional bar in roughly half the code, which is its own kind of merit — less surface to maintain, and a consolidated analytics endpoint that is arguably the better API design.

The gap I flagged in the first draft is now closed: Devin's 42 tests were run and all 42 pass. That settles it — the remaining distance is depth of coverage and two defensive choices, which is real but narrower than the line counts suggest. Both entrants satisfy the brief. If you are picking a winner on the spec alone, it is a draw; if you are picking on what you would rather inherit and extend, the tie breaks on tests and on tenant isolation that cannot be forgotten.
